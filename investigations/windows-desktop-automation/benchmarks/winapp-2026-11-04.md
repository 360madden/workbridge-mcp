> Evidence status: **measured on Joey's live Windows host** through Workbridge MCP. No GUI input, focus, screenshot, VMware guest action, service restart, installation, or production-code change. Results are a narrow, nonrepresentative baseline, not a candidate comparison or proof of action reliability.

## Test A — Workbridge MCP end-to-end latency

Ten sequential cycles. Each cycle called `desktop_windows({app:'explorer'})`, selected the unique visible, adequately sized `Shell_TrayWnd` by structural fields, then called `desktop_inspect({pid,hwnd,process:'explorer',depth:1})` using that **fresh** identity. Every result was checked for `ok:true` and the requested target PID/HWND/process. The caller measured wall time around each MCP call with JavaScript `Date.now()`. It therefore includes connector and Workbridge overhead, not just the WinApp CLI subprocess.

| Metric | Samples | Min | Median | P95* | Max | Mean |
|---|---:|---:|---:|---:|---:|---:|
| `desktop_windows` | 10 | 1,313 ms | **1,544 ms** | 3,323 ms | 3,687 ms | 1,904 ms |
| `desktop_inspect` | 10 | 1,665 ms | **1,915 ms** | 2,980 ms | 3,041 ms | 2,216 ms |
| Fresh enumerate → inspect cycle | 10 | 3,071 ms | **3,677 ms** | 5,672 ms | 5,702 ms | 4,120 ms |

## Test B — individual CLI process startup/operation cost

Five sequential repetitions of each command shape. Invocation was explicitly via `C:\Windows\System32\cmd.exe /d /c` because the terminal resolver rejects the Windows App Execution Alias; WinApp itself runs from the desktop adapter. Fixed, read-only commands:

```text
winapp.exe --version >NUL
winapp.exe ui list-windows -a explorer --json >NUL
winapp.exe ui inspect -w <freshly-verified Shell_TrayWnd HWND> --depth 1 --json >NUL
```

## Source tracing and which starts are avoidable

| Path | Relevant verified behavior |
|---|---|
| `scripts/desktop-ui.mjs:7,81-147,172-227` | Pins WinApp version `0.7.1`; launches a fresh native WinApp child for **each** CLI command; `desktop_windows` does `--version`, then `ui list-windows`; `desktop_inspect` does `--version`, then PID-filtered `ui list-windows`, then HWND-specific `ui inspect`. Each WinApp child has a 15-second timeout. |
| `src/desktop-windows.ts:3-4,39-83` | Exposes bounded `desktopWindows` and `desktopInspect`, passing the read-only script to a separate Node wrapper with a 45-second outer deadline. |
| `src/desktop-cli-runner.ts:68-185` | Starts the Node wrapper with bounded stdout/deadline, avoids ambient authentication credentials, treats uncertain child/grandchild process settlement conservatively. |
| `src/desktop-registration.ts:13-16,36-140` | Currently registers narrow desktop tools and uses an exclusive GUI-turn file lock for captures; not a generic desktop action backend. |
| `src/desktop-session-policy.ts`, `src/desktop-action-policy.ts`, `src/desktop-action-postcondition.ts` | Richer process/session/lease/postcondition constraints exist as **offline** planning/verification components, not production-general UI input. |
| `src/command-executable.ts:5-31` | Workbridge terminal executable resolver requires `stat(...).isFile()`, so it does not resolve the WindowsApps App Execution Alias; explicit `cmd.exe` wrapper succeeded. This is distinct from native desktop adapter operation. |
| `test/desktop-ui.test.mjs`, `test/desktop-windows.test.mjs` | Synthetic tests assert bounded commands, exact PID/HWND, title/process matching, stale-target refusal and injected typed failures. They are historical source tests, **not rerun** in this investigation. |

One normal repeat cycle consisting of caller-side `desktop_windows` followed by `desktop_inspect` starts the WinApp executable **five times**: version + list, then version + list + inspect. Of these:

1. **Avoidable now when the exact target is already known:** the *entire separate* `desktop_windows` call (two starts and one MCP round trip). `desktop_inspect` itself freshly re-enumerates by PID and rejects a missing/mismatched HWND/process/title before inspecting. Skip initial listing only for a previously discovered exact target, and rediscover on stale/missing identity.
2. **Potential optimization with additional design:** repeated `--version` calls (two of five starts per full cycle, one of three within direct inspection). Each direct CLI version probe averaged ~381 ms including wrapper. Removing per-call pin checks requires a trustworthy version-cache invalidation mechanism and explicit tests for live upgrades/replacement. **Do not remove blindly.**
3. **Do not remove without replacement:** the PID-filtered `list-windows` inside `desktop_inspect`, because it implements the fresh target-identity check. Nor remove the HWND-specific `inspect` itself.

Approximate direct CLI cost of a two-tool cycle from measured means: `2 × version 381 + 2 × list 439 + inspect 498 = 2,138 ms`, with PID-listing performance and wrapper differences unmeasured. This is an **illustrative decomposition, not additive proof**. End-to-end median was 3,677 ms. The `desktop_inspect` portion **within the paired ten-cycle test** had a 1,915 ms median; an inspect-only client workflow was **not separately benchmarked**. The difference of separately computed medians (~1,762 ms) is an **estimate** of avoiding duplicate enumeration and transport, not a controlled before/after A/B result.

## Recommended first patch (no production code change made here)

Adopt a small **read-only orchestration rule and regression tests** rather than changing the WinApp version pin or process supervisor:

1. Discover a window once via `desktop_windows`; retain the *exact* PID, HWND, process and optional title as a **read-only lookup hint**, not an action permit.
2. On subsequent read-only inspection of that known target, call `desktop_inspect` **directly** with those exact values. Its internal `ui list-windows -a PID` already refreshes and checks the selected HWND/process/title.
3. On `STALE_TARGET`, generic invalid/uncertain connector failure, app restart, changed title or session context, **stop inspecting and rediscover**; never silently substitute a different window.
4. Keep the current 0.7.1 per-call version pin and fail-closed desktop safety. Any future focus, click, set-value or capture still requires its own fresh session/process-lifetime/geometry/lease checks and independent before/after proof.

### Proposed regression tests

- Unit: fake-runners assert direct `desktopInspect` makes exactly `--version`, PID-filtered `list-windows`, HWND `inspect`; no independent `desktopWindows` call is required for a known exact target.
- Unit: altered PID/HWND/title/process rejects as stale **before** `ui inspect`; no fallback to another target. Validate connector error-mapping separately because externally reported stale-identity errors were generically `INVALID_ARGUMENT` during this baseline.
- Unit: preserve pin failure for a simulated WinApp `0.8.0`, malformed JSON refusal, and no input/focus/capture in the read-only adapter.
- Live read-only A/B: ten warmed repeated taskbar inspect calls with identity revalidation, compare baseline two-tool path vs one-tool path using paired measurements and report medians/p95/failures. No sensitive output.
- Future action-provider gate: simulate PID/HWND reuse, process lifetime/session change, modal windows, ambiguous labels, lock contention, cancellation/timeout, and unverified after-state using disposable app and trusted native event proof. No live RIFT/VM guest input.

## Limitations and operational risks

- Benchmarks involve a trivial, already-running taskbar, not real third-party dialogs, VMware guests, minimized windows, or cold-start behavior; no app state was mutated or independently checked after actions.
- Host CPU usage, Windows version/build, session/DPI, alternate providers, payload sizes, and tail performance under contention were not measured.
- WinApp CLI has a separate workflow arbitration mechanism (`WINAPP_UI_WORKFLOW_ID`, `ui yield`) that must coordinate with Workbridge's existing GUI-turn lock before any new mutating provider is enabled.
- Reusing a stale caller-side target may cause safe rejection and rediscovery; PID/HWND reuse is not completely excluded by the current read-only pair alone. Adding process creation time and session identity should precede general mutating use.
- CLI startup and `--version` are substantial plausible latency contributors; however CMD wrapper timing cannot prove the version check **dominates** latency inside the production Node-spawn path.
- The existing offline DesktopProbe policy and postcondition modules must not be mistaken for an exposed generic production action mechanism.

## Source-only clarification — --interactive is an inspect filter, not a persistent WinApp session

A subsequent **source-only** check of the **pinned WinApp CLI v0.7.1** resolved a potential optimization misconception:

- **--interactive / -i belongs to ui inspect** and filters output to actionable/invokable elements; the handler raises the implicit inspection depth to 8 and filters **after** InspectAsync returns. It does **not** start a terminal prompt, REPL, long-lived UIA context, or stream of automation requests. An auto-depth increase could raise provider work, so it is not a subprocess-startup optimization. Evidence: [SharedUiOptions.cs](https://github.com/microsoft/winappCli/blob/v0.7.1/src/winapp-CLI/WinApp.Cli/Commands/SharedUiOptions.cs), [UiInspectCommand.cs](https://github.com/microsoft/winappCli/blob/v0.7.1/src/winapp-CLI/WinApp.Cli/Commands/UiInspectCommand.cs), and [v0.7.1 UI automation docs, inspect](https://github.com/microsoft/winappCli/blob/v0.7.1/docs/ui-automation.md#inspect).
- **WinApp UI subcommands are one-shot invocations.** [UiCommand.cs](https://github.com/microsoft/winappCli/blob/v0.7.1/src/winapp-CLI/WinApp.Cli/Commands/UiCommand.cs) registers individual verbs, with no general UI server/repl verb. WINAPP_UI_WORKFLOW_ID retains *desktop turn continuity* across separate commands for a short grace, not a persistent application/UIA process; the [coordination docs](https://github.com/microsoft/winappCli/blob/v0.7.1/docs/ui-automation.md#coordinating-concurrent-ui-workflows) explicitly describe independent one-shot commands. The longer-running ui record command is a video recorder stopped through Ctrl+C/stdin, **not** a general command interpreter.
- **The npm programmatic facade still launches the native CLI per call.** [winapp-cli-utils.ts](https://github.com/microsoft/winappCli/blob/v0.7.1/src/winapp-npm/src/winapp-cli-utils.ts) creates a fresh child with spawn and piped stdout/stderr. A **custom persistent .NET UIA sidecar** is technically possible, but Microsoft's [UIAutomation package warning](https://github.com/microsoft/winappCli/blob/v0.7.1/src/winapp-CLI/WinApp.UIAutomation/PACKAGE.md) states that direct package users bypass the WinApp CLI cooperative desktop arbiter; implementing equivalent ownership, exact-target validation, bounded process supervision and recovery would be new engineering.
- **Decision:** first evaluate the *already-available caller-side* optimization in this report: for a previously discovered exact PID/HWND/process, call Workbridge desktop_inspect directly because its adapter re-enumerates and checks the target itself. Rediscover on a stale/changed target. Then A/B benchmark the read-only workflow; do **not** claim a measured speedup yet. Separately benchmark a controlled sbroenne MCP stdio read-only snapshot sidecar before deciding whether any persistent provider complexity is justified.

**Addendum evidence level:** pinned primary-source review only. No additional host commands, measurement, UI input or production code changes accompanied this clarification.
