# Independent source review — other Windows desktop backends for Workbridge

**Date:** 2026-11-04  
**Research lane:** Specialist C, read-only GitHub source/releases/tests review  
**Candidates:** [CursorTouch/Windows-MCP](https://github.com/CursorTouch/Windows-MCP), [DigitalDog1/desk-mcp](https://github.com/DigitalDog1/desk-mcp), [appium/appium-wincore-driver](https://github.com/appium/appium-wincore-driver)  
**Scope:** Compare against the established WinApp CLI / sbroenne research stack; identify reuse ideas, failures, bounded synthetic pilots. **No install, execution, UI interaction, VM access, live-game hook, or production change performed.**

## 🟢 Bottom line

**Retain Workbridge and keep WinApp CLI + sbroenne/mcp-windows as the primary interoperability pilot.** These three sources reveal worthwhile ideas, but none supplies an independently proven, shared cross-provider lease with exact process identity, complete before/after effect proof, GPU/offscreen capture, and bounded modal/hung-provider recovery.

- **🟢 CursorTouch/Windows-MCP:** strongest **second candidate to benchmark for general desktop-agent experience**, due to substantial adoption, active Windows CI, user/AI desktop takeover, UIA timeouts, conditional waits, and fast screenshot pathway. Its click/typing results generally report attempted input, **not** a verified application effect. The local physical-user takeover mechanism cannot coordinate external Workbridge/WinApp/sbroenne agents by itself.
- **🟡 Appium WinCore 4.0.4:** strongest **specialized legacy-accessibility and QA automation reference**, with exact Appium/WebDriver lifecycle, MSAA-backed selection postconditions, large Windows E2E matrix and .NET 10 native helper. Heavy stack; vulnerable to a hung synchronous UIA COM call in its native server; not an MCP server itself.
- **🔴 desk-mcp 1.5.0:** innovative full-pipeline reference for UIA→MSAA→CDP→OCR, differential trees, condition waits, batch, and typed outcomes. **Do not deploy as a trusted unattended Workbridge input backend yet:** source shows verifiable false-success paths, incomplete dry-run/allowlist enforcement, cache-staleness risk, and inconclusive/failing CI. Revisit only after targeted fixes and independently validated synthetic tests.

The findings below are source-level facts or clearly labeled engineering inferences, **not** measured performance on Joey’s desktop.

## A. CursorTouch/Windows-MCP

**What is better than a simple WinApp/UIA caller:** the repository treats the physical user and AI as conflicting desktop owners. README “Desktop control” describes relaxed/balanced/strict gates, AI visual border/cursor indicator, physical movement takeover, a hotkey for takeover, injected key/button cleanup, plus a read-only ControlStatus. It also distinguishes background read-only operations from disruptive foreground input. This is a concrete design reference for Joey’s daily-use PC.

**Wait and UIA reliability:** README defines **WaitFor** conditions text_exists, active_window, element_exists, element_enabled, focused_element with timeout up to 120 s and interval up to 5 s. [tools/input.py](https://github.com/CursorTouch/Windows-MCP/blob/main/src/windows_mcp/tools/input.py) lines 442–508 shows **polling** desktop.get_state every interval, not event-driven UIA subscriptions or a transaction with automatic action verification. README also configures UIA connection 2000 ms and transaction 5000 ms defaults and per-process UIA traversal exclusion. Failed windows can be skipped with error recording, improving resilience when another app is hung.

**Capture:** README snapshot/screenshots use dxcam/mss/Pillow backends and metadata including active windows. This is screenshot-first/desktop-composition capture; the project does not claim WGC private HWND frame capture. Coordinate Click, Type and drag return confirmation that a tool attempted input; e.g. [tools/input.py](https://github.com/CursorTouch/Windows-MCP/blob/main/src/windows_mcp/tools/input.py) lines 237–255 returns “clicked” after desktop.click without reading a postcondition. The project itself documents some Windows XAML drag actions silently doing nothing.

**Limits for Workbridge:** input control is inside this server and its hooks; it is **not a cross-process shared lock**. README explicitly warns user takeover is best-effort, hooks may fault, external PowerShell may continue, and injected holds can briefly overlap physical input. It does not bind a click to a Workbridge job’s exact PID+process-creation-time target. Python 3.14 is usable in Joey’s stated environment but is another runtime/publishing surface alongside .NET 10. The 0.2–0.5 second interaction figure is the project’s estimate, not our benchmark. Default anonymous telemetry is documented; configuration review is needed in a future scoped setup.

**Recommendation:** compare its user takeover, timeout/error taxonomy and fast screenshot UX with WinApp/sbroenne in a **read-only synthetic host pilot**. Never run it concurrently as an independent input controller before Workbridge can acquire and enforce a single common lease.

## B. DigitalDog1/desk-mcp

**Real innovations worth reusing:** source packages four observation layers, MSAA fallthrough for UIA-empty legacy apps, native UIA-pattern direct actions, CDP DOM, Windows OCR, compact/differential tree tokens, read_table, and batch up to 50 sequential operations with result substitution and stop-on-error. [worker.ps1](https://github.com/DigitalDog1/desk-mcp/blob/main/worker.ps1) lines 2332–2400 conditionally waits for element appear/disappear/state with a monotonic deadline, reporting satisfied:false on timeout instead of falsely asserting absence. [server.mjs](https://github.com/DigitalDog1/desk-mcp/blob/main/server.mjs) 956–980 defines verify_state predicates. [uia-native.cs](https://github.com/DigitalDog1/desk-mcp/blob/main/uia-native.cs) 1263–1297 performs SelectionItem then tests IsSelected and reports notSelected when the action had no effect. These are better patterns than “click returned, therefore success”.

**A useful event proof, with a narrower meaning:** [server.mjs](https://github.com/DigitalDog1/desk-mcp/blob/main/server.mjs) 1466–1551 implements computer_browser_click by installing a page-side click event probe through CDP, dispatching mouse events, then reading which DOM element received the event and whether the URL changed. It returns verified:true for a probe hit or navigation. This proves **event delivery or navigation**, **not** that a button successfully saved a file, changed a server record or completed the intended transaction. It can retry when no event is seen, which risks a duplicate side effect when the first action was effective but unobservable.

### Specific blockers verified in the source

| Severity | Source evidence | Why it matters |
| --- | --- | --- |
| **🔴 P0 false verification** | worker.ps1 3162–3164 handles an expected window.exists boolean by mapping true→satisfied, false→unsatisfied, without enumerating or checking any window | A positive window-exists check can pass with no window; a negative check cannot pass even if absent |
| **🔴 P0 false-positive batch status** | server.mjs 768–782 wraps every resolved worker call as a step with ok:true, even if returned payload is data.ok:false (verify_state has this shape); batch allOk checks wrapper fields only | A batch can report allOk:true while the included state verification failed |
| **🔴 P0 incomplete dry-run / allowlist** | worker.ps1 695–719 mutating-tool list omits set_frame, polyline, clipboard_set; Assert-TitleAllowed skips requests with no title. server.mjs 1466–1551 CDP browser_click runs in Node, bypassing PowerShell dry-run/title checks/audit | Unattended routing controls cannot be trusted without Workbridge-enforced common policy |
| **🟡 P1 1.2-second stale verification** | worker.ps1 1445–1454 Get-UiCached returns prior semantic metadata for up to 1200ms; verify_state 3172 calls cached reader | Immediate post-action verification can report old states, either false positive or false negative |
| **🟡 P1 incomplete COM cancellation** | uia-native.cs 111–249 abandons a timed-out STA thread and starts another; blocked COM work is **not forcibly canceled**, and Pump has an infinite loop | Repeated provider hangs can strand threads; server-level watchdog restarts worker but no hard guarantee of isolated provider recovery |
| **🟡 P1 unbounded auxiliary desk wait** | worker.ps1 99–112 RunOnDesk ends in unbounded _deskDone.Wait(); server.mjs 171–190 kills nonresponsive worker at its outer timeout | Input helper can still hang until process watchdog tears down the whole worker |
| **🔴 P0 CI proof not established** | default-branch tree lacks check-docs.mjs; package.json exposes check:docs and smoke.mjs 741–759 invokes missing script, increments fail but does not set failing process exit code. Last observed CI runs marked failure with zero jobs | README’s “85 passed” cannot be treated as current verified CI or a trustworthy shell exit-code gate |

**Capture caveat:** [worker.ps1](https://github.com/DigitalDog1/desk-mcp/blob/main/worker.ps1) 346–361 uses synchronous PrintWindow(PW_RENDERFULLCONTENT) and does **not check its boolean return** before handing back the bitmap. README claims occluded/minimized window capture, but this is highly target-dependent and unreliable for GPU apps; ordinary CopyFromScreen cannot recover unrendered/minimized frames. Microsoft explains synchronous application-participating [PrintWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow) behavior. Do not transfer the minimized-window claim to RIFT or VMware.

**CI detail:** [ci.yml](https://github.com/DigitalDog1/desk-mcp/blob/main/.github/workflows/ci.yml) intends Windows parser, selftest and smoke jobs, but inspected [latest run](https://github.com/DigitalDog1/desk-mcp/actions/runs/37947007849) is failure; its jobs endpoint listed **zero executed jobs**. Therefore no claim can be made that test assertions actually ran or failed on a host. Separately, the code-level missing script and nonfailing smoke exit are independently evidenced. The README says 85 tests pass; we did not run them.

**Recommendation:** copy the ideas (typed outcomes, explicit verify, condition wait, batch receipts, breaker), **not this backend’s unattended policy**. Re-evaluate only after P0 bugs have patches, tests fail reliably at process exit, a CI pass is visible, and all input paths enforce Workbridge leases.

## C. Appium WinCore Driver 4.0.4

**Fit:** [package.json](https://github.com/appium/appium-wincore-driver/blob/main/package.json) requires Appium 4 and modern Node 22.22.2/24.15.0+/26; build uses TypeScript plus a [.NET 10 Windows, self-contained, single-file, win-x64 C# server](https://github.com/appium/appium-wincore-driver/blob/main/csharp/WincoreServer/WincoreServer.csproj). Published npm packages can include a prebuilt native executable; source installs may build with .NET 10 SDK. This matches Joey’s .NET 10 coding interest but adds a full Appium/WebDriver process and driver/session layer. A separate nascent [verisoft-ai/wincore-mcp](https://github.com/verisoft-ai/wincore-mcp) exists for MCP clients; **appium-wincore-driver itself is not a drop-in MCP tool server**.

**Specific strength:** [API.md](https://github.com/appium/appium-wincore-driver/blob/main/API.md) 314–374 and [PatternCommands.cs](https://github.com/appium/appium-wincore-driver/blob/main/csharp/WincoreServer/Commands/PatternCommands.cs) 41–217 show a refined legacy/MSAA postcondition: select, expand and collapse first read existing state, perform UIA/Legacy action, poll for the expected state within a shared **600ms** verification budget, and return InvalidElementState when a legacy action silently failed. UIA-native controls are trusted on success; **Invoke has no semantic postcondition**, only a 50ms delay. If a legacy peer disappears during an action, some paths count that as success; Workbridge should confirm the intended new state separately.

**Legacy and modal UI:** exposes LegacyValue/LegacyRole/LegacyState for grids (VB6, MFC, WinForms DataGridView, DevExpress), [windows:getNativeChildren](https://github.com/appium/appium-wincore-driver/blob/main/API.md) via MSAA, ItemContainerPattern and VirtualizedItemPattern for unmaterialized list items, explicit HWND attachment, getWindows and switchToWindowByTitle. [SessionState.cs](https://github.com/appium/appium-wincore-driver/blob/main/csharp/WincoreServer/State/SessionState.cs) re-resolves root by HWND to withstand WPF peer rebuilds and detects closed HWNDs. However **IsWindow(HWND)** alone does not guard against HWND reuse or a new process with the same title; exact PID + process creation time still belongs in Workbridge.

**Hang hazard:** [JsonRpcServer.cs](https://github.com/appium/appium-wincore-driver/blob/main/csharp/WincoreServer/Server/JsonRpcServer.cs) 37–73 runs one synchronous STA message loop and executes each request inline. [lib/server/client.ts](https://github.com/appium/appium-wincore-driver/blob/main/lib/server/client.ts) 97–121 stores pending requests but does not install per-request timers. A stuck COM UIA provider could therefore block later native requests; Appium/WebDriver HTTP timeouts do not by themselves undo that stalled native thread. Any adapter requires an **out-of-process watchdog that kills/restarts the entire native session**, reattaches to a fresh exact target, and does not replay non-idempotent actions automatically.

**Capture/GPU:** [ScreenshotCommands.cs](https://github.com/appium/appium-wincore-driver/blob/main/csharp/WincoreServer/Commands/ScreenshotCommands.cs) uses System.Drawing Graphics.CopyFromScreen, not WGC or guaranteed GPU/offscreen capture. Screen recording uses ffmpeg gdigrab. Separate capture research still stands.

**Quality signal:** the repo has [C# unit tests](https://github.com/appium/appium-wincore-driver/tree/main/csharp/WincoreServer.Tests), [TypeScript unit tests](https://github.com/appium/appium-wincore-driver/tree/main/test), a Windows [unit-test workflow](https://github.com/appium/appium-wincore-driver/blob/main/.github/workflows/unit-test.yml), plus a [GitHub-hosted E2E workflow](https://github.com/appium/appium-wincore-driver/blob/main/.github/workflows/e2e-test-hosted.yml) with native/MSAA, Chromium, Calculator, input, system, app lifecycle, patterns and recording shards. This is substantially deeper *test infrastructure* than desk-mcp; CI configuration alone does not prove every environment/test case passed. API documents XPath as slow, building full tree XML (around **4.5–6 s for ~3,000 elements** on sampled WPF cases), while native UIA conditions are far faster. Prefer native locators and narrow relative scope for RIFT adjacent apps.

**Recommendation:** retain as a **QA/legacy-controls benchmark and possible code/SDK pattern reference**; do not pull Appium 4 into production solely for UIA clicks. A focused isolated session could test MSAA virtualized grids and verified selection where WinApp/sbroenne fail, after adding a watchdog and Workbridge lease.

## Cross-provider architecture requirement

**No candidate should directly own input in a parallel Workbridge installation.** Six simultaneous reasoning agents can read different surfaces concurrently, but every host physical keyboard/mouse action—and every separate VM guest action—must acquire one Workbridge-issued lease. A backend-local hook (CursorTouch), a batch (desk-mcp), or an Appium session is **not** a shared distributed lock.

Before an action: resolve exact **desktop/session, HWND, PID, process start UTC, executable, VM ID if applicable, window owner/modal chain, DPI and frame timestamp**. After: capture fresh semantic/screenshot evidence and evaluate an **explicit postcondition**, not merely a successful API call. Reject stale/reused process identities, contention, ambiguous match, provider timeout and unseen desktop. Put provider commands behind configurable allowlist and disabled-tool list at the Workbridge boundary, not just the backend.

| Required receipt | Meaning | Failure behavior |
| --- | --- | --- |
| before evidence | target identity, UIA tree/ROI frame, expected precondition | no action if stale/ambiguous |
| lease | Workbridge host or named guest input owner, bounded TTL | wait or reject, no competing click |
| action | provider, operation ID, one bounded intent, elapsed ms | timeout reported as uncertain, no auto replay |
| after evidence | independently sampled state, not cached 1200ms metadata | outcome unknown/unsatisfied is **not** success |
| recovery | release all injected keys/buttons, worker health, stable target rebind | human handoff or synthetic-only recovery |

## Targeted synthetic test plan (no tests run in this lane)

1. **Cross-provider contention:** two dummy hosts / six simulated agent callers; one keyboard/mouse lease per host and per disposable VM, independent capture allowed; verify all tool families (including browser/CDP and clipboard) respect policy.
2. **WinForms modal and legacy DataGridView:** pattern select/expand/invoke, popup owner tracking, MSAA state and virtualized item behavior; compare WinApp, sbroenne and WinCore’s state check.
3. **Nonresponsive provider:** hang synthetic COM/UIA app; test each backend’s bounded return, worker process count, queue health, no stranded calls, and no automatic replay after timeout.
4. **P0 desk assertions:** require window.exists:true on nonexistent window to fail; verify a false state inside a batch forces batch allOk:false; verify desk dry-run blocks set_frame, polyline, clipboard_set and browser_click; require allowlist for coordinate-only call.
5. **Freshness:** click/rename/recreate controls under 1200ms; same HWND process restart and recycled title; demonstrate stale verification/element ID rejection.
6. **Event vs effect:** CDP probe receives click while app deliberately suppresses save; check event-received does **not** equal business postcondition. Simulate navigation before confirmation and prevent blind retry.
7. **GPU capture:** controlled synthetic DirectX window at multiple DPI scales, windowed/occluded/minimized; compare dxcam, PrintWindow, CopyFromScreen and separate WGC/DXGI method; reject blank/stale frame as unavailable.
8. **Test reliability gate:** failure in one assertion must produce a nonzero process exit and visibly red Windows CI; inspect skipped vs failed reasons, no “green because skipped” benchmark claims.
9. **Latency telemetry:** measure median/P95/P99 per tool and entire before→action→after flow under six readers, one writer; distinguish target UI rendering time from RPC and model time.
10. **Operational boundary:** no UAC secure-desktop automation; no unapproved RIFT/VM interaction, no quarantined RIFT-Lab-1 capture, no OBS hook on live RIFT in this investigation.

## Final prioritization

1. **P1:** Keep existing Workbridge operating. Evaluate installed WinApp and sbroenne against the receipt/lease contract first.
2. **P2:** Selectively compare **CursorTouch** for the physical-user takeover and UIA timeout/screenshot experience, in synthetic read-only mode.
3. **P3:** Extract/test **Appium WinCore** MSAA verification and virtualized-item logic if ordinary WinApp/sbroenne fails an important third-party dialog/grid.
4. **P4:** Track **desk-mcp** concepts and patches only; require independent proof that its P0 false-success / guard bypass / test-exit defects are fixed before allowing desktop input.
5. **P5:** Keep GPU, minimized-window, secure desktop and VMware guest problems in the separate non-UIA fallback lane; no one of these projects universally solves them.

**Research confidence:** high for quoted current source paths and release/runtime declarations; medium for applicability to Joey’s actual apps; no live validation of runtime performance or failure recovery. GitHub popularity, badges and author benchmarks must not be treated as acceptance test evidence.
