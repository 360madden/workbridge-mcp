# DesktopProbe next-phase launch decision — investigation only

**Date:** 2026-11-04. **Status:** Design recommendation, **NO GUI run**. Keep daily Workbridge 0.16.4-dev service, 36-slot coordination, current desktop APIs, RIFT/VMware guests and existing GUI-turn quarantine unchanged. No production deployment decision.

## Decision

**Prefer one disposable, on-demand, current-user Windows Task Scheduler entry running the pinned .NET 10 `DesktopProbeWatchdog.exe`, and have that watchdog launch the one hash-pinned `DesktopProbe.exe` WinForms target.** Do this only *after* legitimate recovery of the old RIFT GUI-turn lock/sidecar, source hash verification, exact interactive SID/session preflight, and a quiet host-desktop approval. Task name and helper ID must be unique, `Limited`/`Interactive`, **no `AtLogon` trigger** and no task retry. Capture task registration/status before start and remove only this verified task after all owned children settle. Its narrowly owned `.local/helpers/<id>/registration.json` intentionally persists; this is not a production service update.

Why this route: `docs/interactive-desktop-vm-roadmap.md:53–57,77–93` records actual historical native WinForms GUI visibility and guarded action via the existing `scripts/Manage-HelperTask.ps1`. A directly spawned PowerShell form from the hidden Workbridge command runner previously failed visibility. The manager itself uses `ExecutionTimeLimit=PT0S` (unlimited; `scripts/Manage-HelperTask.ps1:60–70,110–118`), so it does **not** contain a hang. The newly built, synthetic-tested `prototypes/desktopprobe-watchdog` uses an independent ≤110s monotonic child deadline, private kill-on-close Job, atomic shared input lease and target manifest only after native `shown`; it is the narrow missing hard-stop component. **The exact updated watchdog has not yet proven an interactive Scheduled Task launch or resulting window in a current session.**

| Option | Fit / operational overhead | Decision |
| --- | --- | --- |
| 🟢 Existing on-demand helper task → watchdog → disposable fixture | Reuses historically successful Limited/Interactive visible-launch route; bounded watchdog, no Workbridge server registration; one ephemeral task and scoped registration receipt to cleanly account for | **Preferred first controlled GUI test, after release gates** |
| 🟡 Human opens the exact pinned watchdog locally | Can prove same-session GUI without creating a scheduled task; but requires manual click, exact arguments/hashes, provenance receipt and cleanup supervision; higher human overhead and less repeatability | **Fallback if Task Scheduler interactive token fails**, not a parallel launch |
| 🟡 A new private desktop GUI launcher/control-center hook | Could provide repeatable desktop attach and reduce task registration, but adds unproven code, session/focus surface, testing and eventual deployment considerations | **Defer** until existing helper path demonstrably fails |
| 🔴 Direct `terminal_run` GUI/PowerShell Form or unguarded `DesktopProbe.exe` | Hidden command worker historically did not display form; direct fixture bypasses hardened watchdog/lease; user-visible state cannot be trusted | **Do not select** |
| 🔴 Task without fresh ownership/quarantine evidence | Risk of simultaneous desktop activity with physical RIFT and unknown prior action outcome | **Hard HOLD** |

## Provider sequence (do not conflate launch with benchmark)

1. **Quarantine gate first:** existing shared `.tools/desktop-evidence/desktop-input-turn.lock` and linked `desktop-turn-quarantine-*.json` (Nov 2 physical RIFT) are confirmed retained and outcome unknown. Read-only reconciliation classifier has 9/9 synthetic tests, **but no live recovery has run**. Require owner-authorized exact-hash archive/reconcile; do not auto-delete by PID, age or task result. Final watchdog refuses both lock and orphan quarantine.
2. **Offline source/runtime gate:** verify published watchdog, child, managed DLL and allowed helper manager hashes; new runId, no prior task, no other DesktopProbe, bounded evidence directory; confirm same owner SID and `WinSta0\Default`. Reliability reviewer owns unresolved Job/console details, including the Sbroenne native host's extra `conhost.exe` members and mistaken exact-three membership gate; avoid changing that code in this lane.
3. **One quiet host-only GUI pilot:** with user forewarning that opening a small centered WinForms window may take focus, start the exact test-only task *once*. Await native `starting → shown` plus independent PID/start time, HWND, class, session/SID, monitor and baseline foreground. If no manifest/window/lock identity, stop; distinguish process-tree settlement from `no_gui_manifest / unknown_outcome`. No input, screenshots, arbitrary UIA text export, VM or OneDrive target.
4. **WinApp 0.7.1 A read-only sample first:** known PID/HWND, fresh independent native observer before/after, control tree for three synthetic controls only, unchanged counter/foreground. If this succeeds, run pinned Sbroenne v1.3.28 **direct MCP stdio `--tools ui_snapshot` only** under separately proved exact process-tree settlement, not the `wincli` autostart daemon. Sbroenne currently has 0 GUI snapshot calls and its native Job host admission is RED, so **do not include B in the first launch until resolved**. Never compare its 1.107s protocol-only handshake with actual WinApp UIA read latency.
5. **Only if clean:** one A/B pair, then at most 5 read-only samples each across fresh ≤110s watchdog lifetimes. Report separate cold startup, provider-only read, full invocation, native observer overhead, timeout, redacted semantic completeness and verified closure. Defer 30 paired blocks and any synthetic click until evidence shows they change the provider decision.

**Time/latency interpretation:** Existing *measured* WinApp taskbar 10-cycle full discovery+inspect median `3,677 ms`, approximate p95 `5,672 ms` (small N); not a DesktopProbe number. Sbroenne stdio handshake `1.107 s` made **zero UI calls**; no candidate speed winner. A newly visible probe can live at most 110s under the watchdog, but trial setup, user quiet time, one-time task registration and cleanup are separate overhead. Planning estimate **15–30 minutes for one prepared controlled launch and redacted A receipt after recovery**, potentially longer on any TaskScheduler/session or hung-provider failure; **30–90 minutes for small comparative evidence** after the B containment gate. Estimates, not measured durations. Avoid claiming a 36-worker parallel desktop benchmark: one GUI-turn owner per session.

## Host versus VMware boundary

- The first fixture runs on Joey's **host Windows interactive desktop** only. WinApp/Sbroenne host UIA may see VMware Workstation chrome and host dialogs, **not** guest OneDrive dialogs, guest login or RIFT DirectX controls.
- A guest Windows UIA helper later needs its **own guest SID/session, receiver health, input lease, postcondition oracle and VM identity**. Lab1's RIFT receiver/queue quarantine and Lab2's unverified response remain independent blockers. No guest-side install or input in this phase.
- Do not infer that a UI automation helper fixes OneDrive's recurring sync pauses. Diagnose root-cause events separately; host-to-guest hash-verified addon sync is a different option.

## Stop/go and ownership

**GO:** Source-only or isolated synthetic tests; existing day-to-day Workbridge untouched. **HOLD:** real host GUI until old quarantine recovery + exact quiet-window approval + task/watchdog preflight. **HOLD:** Sbroenne comparison until private-Job descendant accounting/semantic exit results green. **HOLD:** all VM/RIFT/OneDrive GUI actions and any production provider replacement.
