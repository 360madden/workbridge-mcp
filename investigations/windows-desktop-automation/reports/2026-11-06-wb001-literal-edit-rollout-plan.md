## Decision and currently verified evidence

- **P1 data-integrity defect in active implementation:** `src/changes.ts:343` (source SHA `c7c6d85c2e0826632758cc0d5a1763529b00723bd2ecb6562e2600ee885cf99b`) and deployed `dist/changes.js:303` both call `content.replaceAll(oldText, newText)` inside **`edit_file`**. JavaScript expands replacement-string tokens `$'` (suffix), `$\`` (prefix), `$&` (match) and `$$` (literal dollar). With PowerShell source containing `$'`, this can duplicate the checked file suffix. Exact count and expected SHA guards alone do not validate the user's desired post-edit bytes.
- **Do not misattribute `write_file`:** `Changes.write` uses `input.content` directly in `writeOrEdit`, then EOL normalization and atomic write. This source path lacks the vulnerable user-supplied replacement string. An alleged direct `write_file` corruption needs its own verified input/output comparison.
- **Independent isolated proof:** commit `2e429692accb53840adeeb7722466a80b3361b96`; in-memory `replaceall-literal-dollar.test.mjs` SHA `1ccd8229c158b34562cf48330a36a2ad17601fcfdb1c17818b647a09b5045e77`; Workbridge job `wd_literal_replace_test_20261106b` exit0, stderr0, 11/11 tests passed in Node 96.0138ms. This demonstrates JavaScript replacement semantics, **not** an installed Workbridge `edit_file` end-to-end acceptance.
- **Minimal future code change:** `src/changes.ts:343` becomes `content = content.replaceAll(oldText, () => newText);`. Keep oldText literal search, exact occurrence count, EOL conversion, optimistic expectedHash, journal/undo semantics, APIs and tool names intact. No in-place hot edit to running `dist`.

## Required regression battery (disposable only)

1. Literal newText tokens: `$'`, `$\``, `$&`, `$$`, and mixed PowerShell strings with multiple such tokens; verify **exact independent expected content and SHA256**. `$1`/`$<name>` are no-capture control cases and must remain literal for a string search.
2. Actual `Changes.edit` and MCP `edit_file` on disposable file: one and multiple matches; CRLF, LF and alternate UTF-8 BOM/UTF-16LE; oldText regex-looking characters; exact Unicode and byte length.
3. Guards and refusal: stale expectedHash, incorrect/zero `occurrences`, duplicate edit targets, oversized replacement, invalid UTF/NUL, missing path, concurrent edit losing the race. On every refusal, original file hash unchanged, operation recorded as failed with no partial file write.
4. Journal correctness: `change_status`, diff, before/after hashes, durable undo, replay of same operation ID, and expected error codes. A pass requires **the entire observed after-file bytes**, not a diff excerpt or hash claimed by a tool alone.
5. `write_file` control with identical dollar strings must round-trip unchanged; if it fails, stop and investigate separately rather than folding into this one-line fix.
6. Full trusted project tests (`npm test`, existing startup/updater/smoke tests), clean package build, independent stdio MCP contract acceptance on a disposable workspace, formatter, and sealed release validation checks. Review both Node runtime and Windows text-encoding paths.
7. Concurrent-agent negative: run disposable, bounded edits across independent workers on **different exact files**, plus same-file expectedHash conflict. No test may touch Joey's RIFT/VM, Windows GUI, active desktop lock or real project data.
